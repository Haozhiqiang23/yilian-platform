## 并发正确性

100名不同患者竞争20个号源，初次发现9个500。日志及InnoDB死锁记录定位超时清理与预约创建交叉持锁；最终先独立清理，再开启创建事务。复测20成功、80约满、库存0、预约及通知各20。

同患者100次并发提交1成功、99冲突拒绝，库存只扣1。数据库触发器分别注入预约/通知写入异常后，库存及预约均回滚，移除触发器后恢复正常。

批量超时联表UPDATE曾令同号源3条预约取消却仅回补1个；按预约条件清理后17→20，重复触发仍20。支付/取消的相反锁序先后在主支付、前置超时检查两处发现，统一预约优先后最终20组无500且状态合法。20组是每组两个请求竞争，不是40请求同时执行或100并发支付容量。

## Redis

同JAR、同库与JWT认证，10线程、每组预热100次，正式3轮每轮300请求，交替先后顺序。温缓存阶段详情SQL900→0，但认证SQL仍执行。三轮P95中位数57.830→33.686ms；两边开启开发SQL日志，收益包含日志输出减少，不能外推生产效果。

## SQL

100000条合成预约、100患者各1000条，医生/科室/号源各1条，支付表为空，是简化分布。两个联合索引配合先分页后关联；同一已加索引库中原查询/改写查询各预热一次并执行7次EXPLAIN ANALYZE，根节点耗时中位数3.113→0.283ms，预约节点实际输出1000→10。16组实际Mapper筛选分页结果一致。不是全表扫描十万行降为10，也不是HTTP响应时间；外层仍可能排序本页，深分页未全面优化。
